# Documentation policy — SCRAP NATION

v1.0 · 2026-11-26. Правила для разработчиков и coding-агентов. Связано с [AGENTS.md](../AGENTS.md).

## 1. Принцип

Документ появляется, когда отвечает на отдельный вопрос, приносит пользу следующему разработчику или фиксирует доказательство, которое иначе потеряется. Не создавать пустые файлы, каталоги, шаблоны и отчёты заранее. Небольшая правка кода не требует обновления всей документации.

Различать намерения, принятые решения и фактические результаты. Отмечать непроверенное как гипотезу или «не проверено». Не выдавать план, черновик, тестовые данные или ожидаемые метрики за результат разработки.

## 2. Единственный источник истины

| Вопрос | Основной источник |
| --- | --- |
| Что за игра и где начать? | [README](../README.md) |
| Как агент должен работать? | [AGENTS](../AGENTS.md) |
| Где проект сейчас? | [PROJECT_STATUS](../PROJECT_STATUS.md) |
| Как должна работать игра? | [GameDesign](GameDesign/) — конкретная спецификация |
| Как устроена текущая/выбранная архитектура? | [Architecture](Architecture/) — спецификация; нереализованное отмечено |
| Какой объём и критерии следующего прототипа? | [MVP](GameDesign/MVP.md) |
| Почему принято дорогое для отмены решение? | ADR |
| Что показал технический эксперимент? | Benchmark report |
| Что показал игровой плейтест? | Playtest report |
| Какой полезный опыт иначе потеряется? | DevLog, только при необходимости |
| Что делать и какие есть дефекты? | [GitHub Issues](https://github.com/redbull101020/SCRAP-NATION/issues), при необходимости Milestones |
| Что фактически изменилось и когда? | Git, Pull Requests; выпуски — GitHub Releases |

Ссылаться на основной источник вместо переписывания подробностей. README не становится вторым GDD; PROJECT_STATUS не становится roadmap, backlog или журналом. ADR хранит историческое обоснование, а Architecture описывает актуальные контракты. Отчёт эксперимента содержит результаты, а ADR — вывод и ссылку на них. Код, настройки и результаты проверок определяют факт реализации; спецификация определяет ожидаемый контракт. Расхождение явно отметить и устранить в рамках согласованной задачи.

## 3. Критерии создания документов

Условие появления — минимальный порог, а не указание заранее создать соответствующий путь. Создать файл в той же задаче/PR, в которой условие стало выполняться, если ниже он обозначен обязательным. Для публичного репозитория действует правило раздела 6.

| Документ / место | Когда создавать | Когда не создавать |
| --- | --- | --- |
| PROJECT_STATUS.md (корень) — обязательный сейчас | Уже ведётся; нужна краткая передача актуального состояния между сессиями/агентами | Не создавать второй status-файл. Можно упразднить после согласования, если Milestones/Issues полностью заменят его функцию |
| ADR: Docs/Architecture/Decisions/NNNN-kebab-case.md — обязательный при существенном решении | Решение затрагивает несколько систем, меняет обязательный backend/пакеты/версию движка, authority, формат сохраняемых данных, важную границу модулей или имеет высокую стоимость отката; до закрепления в production | Обычные локальные реализации, именование, мелкие исправления, настройки баланса; не превращать каждую задачу в ADR |
| Benchmark: Docs/Development/Benchmarks/NNN-kebab-case.md — обязательный при значимом эксперименте | Проведено сравнение/измерение, по которому выбирается технология, проверяется бюджет производительности или требуется воспроизводимое сравнение до/после. P0 ECS-spike — первый запланированный случай; зафиксировать также отрицательный/неоднозначный итог | Разовый просмотр Profiler для локального бага, если достаточно PR/Issue. Не создавать фиктивные таблицы результатов до прогона |
| Playtest: Docs/Development/Playtests/prototype-a-01.md и аналогичные — обязательный при проверке гипотезы | Проведён фактический сеанс/серия сеансов с участниками для проверки игровой гипотезы, включая небольшой пилот A, B или C; сохранять результаты даже при провале | Smoke test разработчика, проверка компиляции, будущий сценарий без участников — это не результаты плейтеста; план остаётся в MVP |
| DevLog: Docs/Development/DEVLOG.md — опционально | Есть значимое открытие, неудачный подход, урок или итог этапа, который важно сохранить и который не отражён достаточно в PR, ADR, benchmark, playtest или спецификации | Ежедневная сводка, список коммитов, дублирование отчётов и статуса. Нет уникального наблюдения — нет записи |
| ROADMAP.md (корень) — отложено | После проверки C (либо согласованного пересмотра MVP) утверждены хотя бы два содержательных этапа за пределами A–C и их зависимости, а MVP.md/Milestones уже не дают удобного обзора направления | Текущие P0/A/B/C уже описаны в MVP. Не фиксировать неподтверждённые сроки и обещания; идеи D+ остаются в концепции до утверждения |
| CHANGELOG.md (корень) — отложено | Появилась первая версионированная сборка, реально распространяемая внешним тестерам/игрокам, и требуется история пользовательских изменений между версиями; GitHub Releases допустим как единственный источник вместо файла | Каждый внутренний коммит, документационный PR или локальный тестовый билд. Не копировать release notes в два места |
| CONTRIBUTING.md (корень) — отложено | Проект реально приглашает внешних разработчиков или начинается первый внешний вклад, требующий объяснить setup, ветки/PR, проверку, лицензии и правила приёма вклада | Один владелец и AI-агенты уже используют README/AGENTS. Не придумывать политику приёма вкладов или лицензию без решения владельца |
| TODO.md / BUGS.md — не создавать | Использовать Issues для отслеживаемых задач, дефектов и критериев приёмки; Milestones для групп задач при необходимости | Не вести параллельный Markdown-backlog. Временный локальный чеклист задачи допустим, но не второй постоянный источник |
| Новая спецификация GameDesign / Architecture — по потребности | У механики или модуля появился самостоятельный устойчивый контракт, который нельзя удобно описать в существующем файле; изменение утверждено в рамках задачи | Не разбивать документ ради дерева каталогов и не описывать нереализуемые на текущем этапе системы как готовые |

Отдельный DECISIONS.md не вести параллельно ADR. Нумерация ADR последовательная (проверить существующие файлы); нумерация отчётов отражает фактические эксперименты/итерации. Папки появятся с первым содержательным файлом.

Если эксперимент начат, но остановлен до замеров и это повлияло на выбор технологии, сохранить причину, отсутствие результатов и ограничения в отчёте или ADR со ссылкой на PR. Не придумывать измерения. Не заводить отдельный документ для обычного технического препятствия, уже полностью описанного в Issue.

## 4. Минимальный состав записи

### PROJECT_STATUS

Ориентир 20–40 строк. Стадия, ближайшая цель, следующий шаг, блокеры, открытые решения, фактический статус компиляции/тестов/билда, ссылки на актуальные задачи и доказательства. Указывать ветку/ревизию или билд для проверки, если известны. Обновлять дату только вместе с содержательным изменением. Не считать непроверенное успешным.

### ADR

Дата и статус (Proposed, Accepted, Rejected, Superseded), контекст, рассмотренные альтернативы, решение и основания, последствия/компромиссы, условие пересмотра, ссылки на доказательства и связанные контракты. Proposed не является разрешением реализовать несогласованное решение; Accepted после согласования. При замене не переписывать историю: отметить Superseded и связать с новым ADR. Для P0 сначала benchmark/фактическое ограничение, затем выбор backend; не объявлять Unity Entities принятым заранее.

### Benchmark report

Дата, цель, сценарий и критерий сравнения, commit/build, Unity/версии пакетов, железо, параметры, прогрев/длительность и методика, измеренные метрики (с единицами), корректность результатов, ограничения, вывод и следующий шаг. Сохранить отрицательный/неоднозначный результат; ссылаться на воспроизводимую сцену/скрипт и артефакты, если есть. Точные технические требования к ECS-эксперименту в [ECS.md](Architecture/ECS.md).

### Playtest report

Дата, гипотезы и заранее выбранные критерии из [MVP.md](GameDesign/MVP.md), commit/build, сценарий, фактическое число участников и завершённых сессий, наблюдения и измерения (числитель/знаменатель), отличия от плана, ограничения, вывод и изменение для следующего теста. Отделять наблюдение от интерпретации. Маленькая выборка не доказывает коммерческий успех; не записывать предполагаемые ответы как отзывы.

### DevLog (если появился)

Дата и этап, уникальное наблюдение/неудачный подход, чему научились, что изменится или что не повторять, ссылка на источник. Не пересказывать историю коммитов.

### Roadmap / Changelog / Contributing (если появились)

Roadmap: направления, очередность, зависимости, критерии перехода, что утверждено и что остаётся гипотезой. Changelog: версия и дата выпуска, заметные для игрока изменения, известные ограничения, ссылка на релиз. Contributing: реальный setup, правила PR и проверок, лицензирование и требования к внешнему вкладу; ссылки на README/AGENTS вместо копирования.

## 5. Когда обновлять документацию

| Событие | Действие |
| --- | --- |
| Изменился этап, следующий приоритет, блокер, открытое решение или факт проверки/сборки | Обновить PROJECT_STATUS; не обновлять только из-за нового коммита |
| Изменён утверждённый игровой/технический контракт | Обновить затронутую спецификацию в том же PR; README/AGENTS — только если изменились обзор/обязательные правила |
| Принято существенное архитектурное решение | ADR по критериям выше, актуальный контракт в Architecture, ссылка на доказательства |
| Завершён значимый технический эксперимент / плейтест | Отчёт с реальными результатами; при необходимости изменение статуса, решения или спецификации, без копирования отчёта |
| Исправлен обычный баг / локальная правка | Commit/PR/Issue достаточно, если контракт, статус и выводы не изменились |
| Выполнен выпуск | Release notes в одном выбранном источнике; обновить ссылки и статус только если изменился актуальный контекст |

В начале задачи читать AGENTS и PROJECT_STATUS, затем документы затронутой системы. Перед завершением проверить применимые условия, обновить только нужные файлы и назвать их в отчёте/PR. Если не требуется ни одно обновление, не создавать формальную запись. Не расширять scope или не менять утверждённые решения ради согласованности текста без разрешения.

Если статус отстал от кода, проверять факты и обновлять его; не делать предположений о локальных файлах владельца или незагруженных ветках. Если обнаружено противоречие между спецификациями, обозначить его и решить в рамках поручения, а не silently менять игру.

## 6. Публичность и проверка

Репозиторий публичный. Не сохранять персональные данные тестеров, контакты, записи голоса/видео, конфиденциальные отзывы, секреты, локальные абсолютные пути или закрытые коммерческие материалы. Публиковать агрегированные/обезличенные наблюдения и только разрешённые артефакты. Если доказательство нельзя раскрыть, указать безопасное ограничение и согласовать допустимую форму отчёта; не публиковать приватную ссылку без разрешения.

Проверять относительные ссылки, соответствие фактическим файлам и согласованность статуса. Не ссылаться как на существующие на ещё не созданные отчёты. Не заявлять успешные сборки/тесты/замеры без фактических данных.

**Текущее решение:** PROJECT_STATUS и этот регламент существуют сейчас; ADR, Benchmarks, Playtests, DevLog, Roadmap, Changelog и Contributing появятся только по соответствующим условиям. GitHub Issues остаются источником задач. Не создавать пустые каталоги ради структуры.
