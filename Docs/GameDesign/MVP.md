# MVP v0.2 — поэтапная проверка интереса

[Концепция](Concept.md) · [NPC](NPC.md) · [Экономика](Economy.md) · [ECS-spike](../Architecture/ECS.md)

**Цель:** как можно раньше проверить, интересно ли создавать условия развития жителей. A, B и C — последовательные итерации одного проекта. P0 не является отдельной игрой и не должен задерживать A неопределённым технологическим исследованием.

## P0 — технический фундамент

- [ ] Импорт Unity 6.6 Universal 2D, Git, версия и пакеты зафиксированы.
- [ ] Герой и камера на плоской карте; минимальный session/bootstrap и tick.
- [ ] Куча с конечным запасом, автономный сборщик, доставка в ломбард, одна проверяемая транзакция.
- [ ] Короткий ECS-spike на той же задаче; выбрать один production-backend до развития профессий/боя. Если spike не даёт основания переходить, закончить A на простом C#.
- [ ] EditMode: запас не отрицателен, два NPC не забирают последнюю единицу дважды; повторный Play Mode без дубликатов.

**Выход:** сквозной цикл работает, решение о backend зафиксировано кратко. Не требовать 5000 NPC, полный save system, сетевой код или окончательный рендер.

## A — «Живая свалка», 3–5 минут

**Проверяет H1 (интерес к NPC) и H2 (авторство игрока).**

- [ ] ГГ может разместить/активировать ломбард и металлоприёмник, изменить один приоритет/распределение возможностей.
- [ ] Одна конечная куча достаточной ёмкости, две профессии, ограниченный приток NPC.
- [ ] Тележка: сбор и сдача; личный прогресс; гарпунщик.
- [ ] Барахольщик надевает 1 элемент за раз, комплект из 3; железник.
- [ ] Улучшение видно на персонаже и сохраняет ID. Продвинутый NPC продолжает мирную работу.
- [ ] Простой HUD: склад, состояние кучи, прогресс и понятная причина действия. Placeholder sprites достаточны.
- [ ] Первые внешние тесты до B.

Сценарий: 0–1 мин — герой и первое здание; 1–3 мин — автономный труд и первое улучшение; 3–5 мин — выбор другой возможности и шанс вырастить второго жителя. Настраивать расстояния/таймеры так, чтобы была реальная возможность повторения. **Не нужны атаки, караван, дисковые saves, сложная телеметрия, глобальная карта.**

Критерий перехода: игроки замечают и понимают развитие, часть самостоятельно пытается его повторить, решения меняют наблюдаемый результат. Если H1/H2 не подтверждаются, итерация A прежде B.

## B — «Борьба за ресурсы», 5–10 минут

**Проверяет H3 (стратегическая дилемма) и ценность людей.**

- [ ] Сохранить ядро A; ограда, ремонт, тревога и один тип врага.
- [ ] Одна-две волны с предупреждением, трата груза в бою, потеря временной брони, возвращение к работе.
- [ ] Один локальный ценный спот; конкурент ИИ использует те же правила контроля и доставки.
- [ ] Выбор приоритета/охраны: дополнительная добыча ценой меньшей защиты лагеря. Возможен частичный успех и отступление.
- [ ] HUD угрозы, контроля и доставки; понятные последствия выбора.

Плейтест B отдельно от C: в 0–3 мин подготовка, затем предупреждение/нападение и конфликт за спот. Проверить, что игрок не выбирает один очевидный вариант всегда. Никакого PvP/сервера, нескольких регионов или полного сохранения.

## C — «Кочевая цивилизация», 15–20 минут

**Проверяет H4 (переезд как развитие) и H5 (желание продолжить).**

- [ ] Две конечные кучи, один предупреждённый сброс; 2–3 волны с ростом угрозы от богатства/стоянки.
- [ ] Опция остаться или переехать; обычный и рискованный район с понятной наградой.
- [ ] Один переезд, повторное использование сцены или двух простых конфигураций.
- [ ] В памяти сохранить ID, имена, профессии, прогресс, экипировку и груз; восстановить NPC и возможность добычи. Цена переезда читаема; известность сохраняется.
- [ ] Завершение после удержания лагеря или разворачивания нового; при гибели ГГ/всех жителей — досрочный исход. Не требовать переезда от каждого игрока.
- [ ] Плейтест; решение о дальнейшей разработке.

Сценарий C: 0–3 мин — управление/стройка; 3–6 — улучшение и нападение; 6–12 — сброс/спот; 12–20 — давление, выбор и последствия. Если игрок остался, проверить осмысленность этого выбора; для проверки сохранения нужно достаточно фактических переездов, при необходимости отдельные тесты C.

## Первые параметры (гипотезы, не утверждённый баланс)

| Параметр | Начальное значение / примечание |
| --- | --- |
| Старт | Флаг, два бродяги, 12 хлама |
| Население | 4–8 после притока; ограничить рабочими возможностями |
| Залежи | A: одна ~40 единиц; C: 40 и 30, плюс сброс |
| Тележка | 4 предмета, 2 полные сдачи до улучшения (или 8 сданных единиц) |
| Временная броня | 3 слота, один элемент за 15–30 с |
| Здания | Ломбард / металлоприёмник / ограда по 4 хлама |
| Улучшение | 2 хлама за комплект; переплавка 3 элементов даёт 3 хлама однократно (см. Economy) |
| Темп A | Первое улучшение примерно 2–3 мин, следующее действие до конца 5 мин |
| Темп C | Первое улучшение до 3–5 мин; нападение ~5-я мин; сброс ~7-я; караван с ~12-й |
| Угроза | Риск, богатство, стоянка, сохраняемая известность; коэффициенты по тесту |

Параметры A/B/C задавать одним конфигом с пресетами, не дублировать игровые правила. Если запасы заканчиваются раньше доступного действия, скорректировать размеры/темп или показать альтернативную добычу. Не строить из таблицы 1:1 весь production balance.

## Проверка гипотез

Ориентир 8–12 внешних тестеров на итерацию; пороги ниже приведены для 10 и масштабируются как доли. Это качественный прототипный сигнал, не статистическое доказательство.

| Гипотеза | Наблюдаемое поведение / ориентир |
| --- | --- |
| H1, A | ≥7 замечают и объясняют улучшение без подсказки; ≥6 сами инициируют следующую попытку/создают возможность для следующего NPC при доступном времени |
| H2, A | ≥7 намеренно меняют здание/приоритет и объясняют ожидаемый результат; действие действительно влияет на состояние |
| H3, B | ≥6 объясняют выбор добыча/охрана/отступление; фиксировать случаи частичной добычи, разных решений и потерь. Если один путь всегда доминирует, пересмотреть дилемму |
| H4, C | ≥6 понимают выбор района/стоять или ехать и сохраняемые достижения; отдельно среди фактически переехавших проверить, что большинство узнаёт своих NPC и способно возобновить цикл |
| H5, C | ≥7 хотят ещё сессию, ≥5 добровольно начинают её при реальной возможности (отдельно от ответов в анкете) |

Сначала наблюдать без объяснения «уникальности» проекта, затем спрашивать о причинах решения и интересе. Записывать моменты ожидания, непонимания, повторной инициативы. Не подменять интерес распознаванием UI. Набор критериев и доступное время фиксировать до теста, не менять пороги задним числом.

### Минимальные измерения

В A достаточно ручного протокола и простого debug-журнала: spawn_npc, item_collected, deposit, upgrade, build, priority_change, отметка первого и повторного улучшения. В B по мере нужды raid_warning, raid_end, spot_enter, spot_contested, loot_delivered. В C migrate_choice, migrate_complete, replay_start и итог. Содержать tick/сессию, не собирать лишние персональные данные; без внешнего аналитического сервиса.

Если A не подтверждён, не лечить это количеством контента. Если B не подтверждён, менять стоимость отвлечения людей и читаемость конфликта. Если C не подтверждён, менять цену и пользу переезда. Не делать выводов о производительности, коммерческом успехе или PvP по одному тесту.

**Вне A–C:** онлайн, сложный AI, вертикальные карты, процедурная генерация, полноценная торговля, сложные потребности, десятки профессий, сюжетная кампания, дисковые saves (отдельная последующая задача), продакшен-арт.
