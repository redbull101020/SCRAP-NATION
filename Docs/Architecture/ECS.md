# ECS / DOTS — ранний эксперимент и решение

[Обзор](Overview.md) · [Симуляция](Simulation.md) · [MVP](../GameDesign/MVP.md)

**Статус:** pending P0 spike. Unity Entities — кандидат для production simulation, не обязательный выбор. Hybrid означает отделение симуляции от Unity views, а не необходимость писать две игры. Не откладывать выбор до конца C.

## P0 spike

Ограничить объём одной-двумя короткими рабочими сессиями разработки. Если интеграция пакета или обучение блокируют цикл, закончить A на простом C# и записать основания. Это ограничение объёма эксперимента, не срок релиза.

1. Общая задача: NPC со стабильным ID, движение по X, поиск слота у конечной кучи, сбор, доставка в ломбард, начисление ресурса/личного прогресса.
2. Базовый C# вариант: компактные структуры/коллекции и централизованные системы без универсального ECS. Минимальный Entities вариант: unmanaged data, MovementSystem, JobSelectionSystem, ScavengingSystem, DepositSystem; тесты тех же инвариантов.
3. Переиспользовать только общие контракты и тест-сценарий. Не переносить бой, караван и все здания ради benchmark. Изолировать эксперимент в ветке или временной тестовой сборке, не заставлять production зависеть от обоих вариантов.
4. Views: одинаковые SpriteRenderer GameObjects, привязанные к стабильным ID, в режиме с графикой. Сначала измерить headless simulation, затем одинаковый рендер. Проверить совместимость пакетов, версию Entities, компиляцию и lifecycle.
5. Сравнить 100/500/1000 NPC на одинаковом seed, числе целей/действий и длительности. 50, 250, 5000 — дополнительные сценарии при необходимости, не условие MVP.

## Как выбрать

- Корректность обязательна: равные сценарии и проверка остатков/доставок/ID, отсутствие двойных транзакций, понятный порядок tick.
- Замеры: p50/p95 tick CPU, frame time при одинаковых views, память, GC allocations, время main thread/Jobs, время на реализацию и сложность отладки. Development Build с одинаковым железом/настройками, прогревом и длиной прогона; документировать версии. Профилировать также сборку без Profiler overhead при необходимости.
- Ориентир для PC — 60 FPS (16,7 ms на кадр), не обещание. Целевой масштаб и бюджет simulation согласовать на фактическом железе до сравнения; 500/1000 NPC здесь стресс-сценарии, не утверждённая вместимость игры.
- Если Entities существенно лучше укладывается в согласованный бюджет при целевом количестве NPC, либо обеспечивает нужную масштабируемость с приемлемой стоимостью разработки, выбрать его на P0. Если простой C# проходит бюджет с запасом, а ECS дороже и не даёт необходимого преимущества, выбрать C#. При неопределённости предпочесть обратимое и более простое решение, не бесконечный benchmark.
- Результат: фактический benchmark report (версии, замеры/ограничения) и короткий ADR с выбранным backend, причинами, условием пересмотра и ссылкой на отчёт. Пути и критерии — [DocumentationPolicy](../DocumentationPolicy.md). Не считать поддержку ECS доказательством преимущества. Один production-вариант; альтернативный spike удалить или оставить изолированным в исторической ветке.

## Если выбран Unity Entities

- Hot data: unmanaged IComponentData, buffers при необходимости; не вводить managed ECS components (направление устаревания и доступность проверять по установленной версии). ISystem, Burst/Jobs там, где данные и API совместимы.
- Core ID постоянны; Entity — runtime handle, не ключ сохранения и не личность. Одна entity на NPC в simulation; сопоставление view через ID. Не копировать изменяемое здоровье/груз/профессию в GameObject в роли второго источника истины.
- Явный simulation update group/driver с фиксированным tick, определённые зависимости и порядок фаз. Если используется встроенная fixed-step группа, не шагать эту же симуляцию из отдельного accumulator.
- Structural changes через подходящий ECB/playback, корректные dependencies, lifetime, safety checks и Dispose NativeContainers. Не вызывать Complete на каждого NPC. Jobs не читают UnityEngine.Object/managed API. View sync выполняется на main thread после нужной зависимости.
- Baking/SubScenes только если упрощают конкретный авторинг. Не требовать EntityScene для каждого региона. Нет обязательного Entities Graphics и Netcode.

## Если выбран простой C#

Компактные структуры/коллекции, явные системы и tick, команды и snapshots. Не писать собственный универсальный ECS; не пытаться имитировать все API Entities. Переход в будущем может потребовать рефакторинга, поэтому сохранять контракты, а не искусственно абстрагировать весь backend. Collections/Jobs/Burst можно внедрять точечно после замера.

## Рендер: самостоятельный эксперимент

| Объект | Базовый путь | Возможный эксперимент |
| --- | --- | --- |
| ГГ/многослойный NPC | SpriteRenderer + SortingGroup, Animator | Sprite Library/Resolver, GPU skinning при подтверждённой поддержке |
| Мусор и фон | Tilemap/SpriteRenderer | RenderSprite/RenderSpriteInstanced для однородных объектов |
| Простые мутанты, снаряды | SpriteRenderer, pooling по необходимости | Instancing при выигрышном batching |
| UI / свет | GameObjects / URP 2D | Не менять ради ECS |

RenderSpriteInstanced группирует экземпляры одного спрайта; сортировка и culling группы могут конфликтовать с перекрытием персонажей/экипировки. Лимиты batch, shader/instance data, освещение, маски, прозрачность и порядок проверять по Unity 6.6 API и отдельному тесту. Не обещать устранение GameObjects или прирост FPS. Сложная анимация не зависит от решения по ECS.

Сначала профилировать реальную нагрузку. Избегать сканирования NPC × цели в каждом tick, лишних аллокаций, Find/GetComponent в горячем пути; registry, распределённые решения, индекс по X и pooling по мере необходимости. Simulation LOD удалённых регионов — после A–C.

Документация для сверки версии: [Unity Manual 6.6](https://docs.unity3d.com/6000.6/Documentation/Manual/index.html), [Unity Scripting API 6.6](https://docs.unity3d.com/6000.6/Documentation/ScriptReference/index.html). Пакетные API проверять по версии из manifest/lock.
