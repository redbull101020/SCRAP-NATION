## Время

Один владелец времени на сессию, SimulationClock или эквивалент. Стартовая гипотеза 20 ticks/s (50 ms); изменение требует повторного теста темпа, не смены игровых правил. Движение/бой — каждый tick, выбор цели NPC каждые 4–5 ticks с разнесением, периодическая экономика/производство около 1 Hz, транзакция при завершении действия.

Frame input получает команды и передаёт их с порядком. Один driver фиксированного tick. Для managed C# возможен accumulator с лимитом catch-up steps; для ECS либо собственный driver, либо встроенная fixed-step группа, не оба. При перегрузке не терять тики молча; измерять backlog, явно замедлять симуляцию при необходимости. Pause останавливает игровое время и не блокирует интерфейс. Views могут интерполировать позиции между snapshots; проверять отзывчивость ГГ на 20 Hz, частоту скорректировать по тестам.

Хранить таймеры в ticks или однозначно конвертируемых единицах. Правила не читают Time.time, DateTime.Now, глобальный UnityEngine.Random. Явный seed/RNG; порядок спорных операций не зависит от обхода Dictionary/Update/jobs. Фиксированный tick и seed помогают воспроизвести сценарий, но не гарантируют межплатформенную или сетевую детерминированность.

## Порядок одного tick (базовый)

1. Принять/валидировать команды и доступность целей.
2. Выбрать/зарезервировать задачи; разрешить перемещение.
3. Разрешить бой, смерть, изменение контроля спотов (когда B реализован).
4. Завершить допустимые сбор, сдачу, строительство, улучшения. Проверить, что NPC жив, цель доступна и стоимость/остаток допустимы.
5. Обновить угрозу, приток и lifecycle; применить отложенные изменения коллекций.
6. Подготовить события и read model.

При одинаковом tick конфликтующие транзакции разрешать в стабильном документированном порядке (tick + sequence или явный tie-break ID). Если задачи отменены, освободить reservations; мёртвый NPC не завершает сдачу. Не делать события второй точкой начисления. ECS-system order и ECB playback должны соответствовать тем же правилам. Дополнительные фазы вводить по реальной задаче и описывать.

## Идентичность и runtime data

- Типизированные ID или эквивалентные однозначные ключи для NPC, зданий, залежей, фракций, регионов, караванов. Instance ID не равен definition ID. Не переиспользовать ID внутри кампании.
- NPC хранит принадлежность, регион, позицию, профессию, задачу, активность, боевой режим, здоровье, экипировку, груз, личный прогресс. В A вводятся только необходимые поля. Ни одно из них не зависит от того, активен ли view.
- Definition/config считывается из ScriptableObject в runtime data на старте сессии. Не изменять asset при Play Mode и не использовать изменяемый static config для разных сессий.
- На MVP плоское движение по X, интервалы/простые зоны. Не создавать NavMesh, многоэтажную навигацию и Rigidbody на каждый предмет. Если Physics 2D используется, явно определить authority и адаптер; нельзя независимо обновлять Transform и position в simulation.
- Мост views связывает ID и текущий объект; при удалении/возврате в пул очищает старые подписки и visuals. Нет обязательного пула для редко создаваемых объектов.

## Команды, задачи и операции

Примеры контрактов (имена не обязательны): BuildCommand, SetPriorityCommand, AlarmCommand, MigrateCommand; события NpcUpgraded, ResourceDeposited, SpotControlChanged. Валидация на стороне simulation; результат доступен UI, события после успешной операции.

Reservation — временное право на слот, не собственность над материалом. Извлечение и доставка проверяют наличие, вместимость и текущий контроль непосредственно в момент применения. Освобождать reservation при отмене/гибели/удалении цели/переезде. Одновременная работа и бой исключаются общим арбитром задач. См. NPC/Economy.

## Переезд и хранение

**A/B:** состояние сессии в памяти, не требуется save framework.

**C:** достаточно согласованного in-memory snapshot на границе tick. Переезд:
1. Проверить участников, место назначения, вместимость/цену.
2. Собрать manifest; отменить или завершить задачи/reservations по правилам.
3. Зафиксировать NPC и груз ровно один раз; подготовить новый регион без второго действующего экземпляра этих NPC.
4. При успешной инициализации переключить authority на новый регион, восстановить views. При ошибке не терять последнюю согласованную сессию.
5. Повторная команда переезда не клонирует людей и груз. Время стоянки сбрасывается; переносимая известность сохраняется.

Повторно используемая сцена с параметрами района допустима. Не строить фоновую симуляцию всех регионов до отдельной задачи. Не привязывать глобальное состояние к жизни scene object.

**После проверки C, если нужны дисковые saves:** versioned DTO со схемой, tick, RNG state (где нужно), регионами, ID, экипировкой, грузом и сохраняемыми остатками/постройками. Сериализовать постоянные данные, не сырые ECS chunks, runtime handles, GameObjects или делегаты. Снимок на согласованной границе tick после применения изменений; запись через временный файл и безопасную замену в поддерживаемой среде, проверка ошибок и схемы. Не перезаписывать неизвестный/повреждённый save молча. Совместимость/миграции схемы — при появлении реальных сохранений.
